二、业务范围

角色：
- 普通用户：浏览、提交菜品、发表评价、点赞、举报、上传图片。
- 审核员：审核菜品、处理举报、隐藏违规评价。
- 管理员：维护学校、食堂、档口、菜品及用户角色。

除角色权限外，必须检查资源归属。
用户不能修改他人评价、绑定他人图片或自行提升权限。

数据层级：
学校 → 食堂 → 档口 → 菜品 → 评价。

第一版不加入：
支付、秒杀、配送、餐品预约、AI 客服、微服务、
Kubernetes、分库分表或复杂推荐算法。

核心流程：

A. 菜品发布
用户选择档口并提交菜品
→ 待审核
→ 审核通过后公开。
管理员可以直接维护菜品。

B. 评价
用户查看已发布菜品
→ 提交 1～5 星评分及文字
→ 保存评价并更新评分统计
→ 提交事务
→ 失效相关缓存。

同用户对同菜品最多保留一条评价记录。
支持修改、软删除与恢复。
用户删除状态与审核隐藏状态应分开表达。
只有未删除、未被审核隐藏的评价计入评分。
用户编辑或恢复评价不能绕过审核隐藏。

C. 排行榜
按学校、食堂查看加权榜单。
返回平均分、评分人数、加权分和榜单生成时间。

使用：
score = v / (v + m) × R + m / (v + m) × C

R：菜品平均分。
v：有效评分人数。
C：所属学校全部有效评分的平均值。
m：可配置先验权重，不是硬性准入门槛。

明确零评分规则和并列排序规则。
不将该公式描述为能识别恶意刷分。

D. 图片
上传并校验
→ 保存原图与图片处理记录
→ 异步生成缩略图
→ 更新状态
→ 用户查询结果。

E. 内容治理
举报评价
→ 审核员处理
→ 必要时隐藏评价
→ 同事务更新评分统计和管理审计记录
→ 失效相关缓存。

三、工程要求

1. 数据与事务

使用迁移管理数据库，不以 create_all 代替迁移。

必要约束：
- 评价 UNIQUE(user_id, dish_id)
- 点赞 UNIQUE(user_id, review_id)
- 评分范围 1～5
- 必要的外键、非空约束和查询索引

金额使用 DECIMAL，时间统一使用 UTC。

维护菜品 rating_sum、rating_count，
平均分由总分和人数推导。

评价新增、修改、删除、恢复、隐藏与取消隐藏，
必须与评分统计变更在同一事务中完成。

设计统一加锁顺序，处理：
- 并发首次评分
- 同用户并发改分
- 多用户同时评分
- 修改与删除竞争
- 审核隐藏与修改竞争

唯一约束负责最终防重，不能仅依赖先查后写。
对冲突和事务失败返回明确结果，避免无限重试。
提供评分统计校验与修复命令。

2. 鉴权

复用并理解模板的密码哈希、登录及 Access Token。
增加所需角色与资源权限。

后续阶段实现 Refresh Token 轮换及撤销：
- 不保存明文 Refresh Token
- 防止同一令牌并发刷新得到多个有效后继
- 明确退出后 Access Token 是否立即失效
- 实现、文档和测试必须保持一致
- Redis 故障时不得静默放行受保护操作

3. 幂等与分页

点赞、取消点赞采用设置目标状态的接口，
不用重试会反转结果的 toggle 设计。
重复请求不能重复计数。

评价列表使用 created_at + id 游标分页，
测试时间戳相同、页边界及记录变化场景。
说明游标分页并不自动提供快照一致性。

4. 缓存与限流

使用 Redis 缓存菜品详情和榜单，采用 Cache Aside。

实现：
- 不存在资源的短 TTL 空值缓存
- TTL 随机抖动
- 热点缓存重建互斥
- 锁唯一标识、租约、安全释放
- 有界等待与查询降级
- 数据库提交后失效缓存
- 缓存故障时普通查询可回源数据库
- 用户或 IP 维度的原子限流

普通查询与鉴权的故障策略应区别处理。

解释更新数据库后删除缓存的竞争窗口。
设计 TTL、版本或补偿策略，明确实际一致性保证。
全校平均分 C 变化会影响多个菜品的加权分，
榜单刷新不能只考虑被评价的那一道菜。

不为凑技术点同时增加多种缓存和锁方案。

5. 异步任务

Celery + RabbitMQ 用于图片缩略图处理。

必须有：
- 持久化处理状态
- 幂等消费
- 有上限的退避重试
- 永久错误与暂时故障区分
- 失败查询及人工重试
- Worker 重启后的恢复验证

解决数据库记录已提交但消息投递失败的问题。
优先采用持久化任务记录与定期补偿扫描；
如选择 Outbox，先解释必要性和复杂度。

不宣称消息只会消费一次。
重复投递和重复执行必须不会破坏结果。

6. 文件与安全

校验图片大小、实际格式、可解码性及解码后尺寸。
对象名由服务端生成，禁止依赖用户路径。
MinIO 默认私有，按可见性及权限提供访问方式。
校验图片归属与绑定关系。
配置从环境变量读取，不提交密钥。
日志不记录密码或完整令牌。

7. 可维护性

沿用模板结构做适度模块化：
路由、请求响应模型、业务服务、数据库模型、
必要的数据访问、任务和测试。

事务边界明确，避免内层随意 commit。
不把业务逻辑全部塞进路由。
不创建没有实际作用的大量抽象层。

提供结构化日志、request_id、请求耗时、
存活和就绪检查。
